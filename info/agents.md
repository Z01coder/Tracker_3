# Техническое задание — «Такт»

## 1. Название продукта и описание

**«Такт» — командный трекер задач с канбан-доской и ролями.**
Деловое веб-приложение для небольшой команды разработки (до 5 человек): проекты, канбан-доска задач по статусам, приоритеты, исполнители и комментарии. Требует входа по логину и паролю; права разграничены по ролям «админ» и «программист».

> Название «Такт» — деловое, короткое, отсылает к ритму командной работы. Трекер с урока в примере назывался NordFlow — «Такт» сознательно отличается: это отдельный кейс для портфолио.

## 2. Цель проекта и целевая аудитория

**Цель:** заменить «разрозненные таблицы и мессенджеры» внутренней командой разработки сайта. Руководитель держит задачи в одном месте, программисты видят свой фокус, руководитель видит прогресс по колонкам доски.

**Целевая аудитория:**
- Небольшая студия/команда из 2–5 человек, ведущая один–два веб-проекта (из заказа).
- Руководитель/тимлид — управляет задачами и пользователями (домысел: у заказчика есть «те кто ставит задачи» и «те кто их делает», это прямо следует из ролей в заказе).
- Программисты — выполняют и комментируют задачи (из заказа: «3 программиста»).

## 3. Что упразднено из заказа и почему

| Пункт заказа | Решение | Основание |
|---|---|---|
| Установка системы контроля версий (VCS) | **Вне скоупа** | Нет доступа к сайту заказчика; вне рамок урока (там только трекер) |
| Установка трекера **внутрь существующего сайта на CakePHP** | **Вне скоупа** | Нет доступа к сайту; трекер делается автономным веб-приложением, в которое заказчик потом сам встраивает ссылку |
| «Требуется сделать срочно» | Учтено как требование к **скорости MVP**, не к объёму фич | Деловая норма — не раздувать MVP |
| Развертывание на сервере заказчика | Только **инструкция по деплою** (Railway) в README | Публикация выполняется студентом отдельно из урока |

## 4. Вопросы «клиенту» и принятые ответы

1. **Регистрация нужна или учётки создаёт администратор?**
   → Регистрации нет: администратор создаёт и деактивирует учётки сам (безопасность; в заказе ровно 5 аккаунтов).
2. **Программист видит все проекты или только те, куда назначен?**
   → Видит все проекты и все задачи, но не может создавать/удалять проекты и пользователей (домысел: команда маленькая, все работают по одним проектам; разграничение — на уровне управления, не видимости).
3. **Какие статусы задач достаточны для MVP?**
   → 4 колонки: «Бэклог / В работе / На проверке / Готово» (стандарт урока, соответствует духу Jira).
4. **Нужны ли вложения файлов в задачи, e-mail уведомления, история изменений?**
   → Нет, это допродажи к MVP (домысел: для 5 человек хватит комментариев; не усложняем первый релиз).
5. **Что должно быть видно при первом запуске?**
   → Демо-проект «Сайт CakePHP — поддержка» с задачами по статусам, приоритетам и комментариям, чтобы проверить роли сразу после входа.

## 6. Экраны и функции

### 6.1 Экран входа
- Назначение: авторизация.
- Элементы: логотип + название, поля «Логин», «Пароль», кнопка «Войти».
- Действия: вход; при ошибке — сообщение на русском. После входа → список проектов.

### 6.2 Экран «Проекты»
- Назначение: список проектов, вход в проект.
- Элементы: список карточек проектов (название, краткое описание, счётчики задач по статусам), кнопка «Создать проект» (только админ).
- Действия: открыть проект (→ доска), создать / отредактировать / удалить проект (только админ).

### 6.3 Экран «Канбан-доска проекта»
- Назначение: основное рабочее пространство.
- Элементы: 4 колонки — «Бэклог» / «В работе» / «На проверке» / «Готово»; карточка задачи (название, метка приоритета, аватар-инициалы исполнителя, дедлайн); кнопка «+ Задача»; фильтры (исполнитель, приоритет, поиск по названию, «сброс фильтров»); колонки считаются.
- Действия: создать задачу; открыть карточку задачи; **перемещение между колонками кнопками** («→» следующий статус, «←» предыдущий) — drag&drop не делаем, решение зафиксировано; удалить задачу.

### 6.4 Карточка задачи (модальное окно)
- Назначение: просмотр и редактирование одной задачи + обсуждение.
- Элементы: название; описание; поля: статус, приоритет (Низкий / Средний / Высокий / Критический), исполнитель (выбор из 5 пользователей), дедлайн (дата); блок комментариев (автор, дата, текст); поле ввода нового комментария.
- Действия: сохранить изменения; добавить комментарий; редактировать/удалить комментарий (свои — любой, чужие — только админ).

### 6.5 Экран «Пользователи» (только админ)
- Назначение: управление учётками.
- Элементы: таблица (логин, имя, роль, статус «активен/деактивирован», создан), кнопка «Создать пользователя», форма создания/редактирования (логин, имя, роль, пароль).
- Действия: создать пользователя; изменить имя/роль/пароль; деактивировать (вход запрещён, задачи остаются, исполнителем деактивированного быть нельзя); активировать обратно.

### 6.6 Шапка (везде после входа)
- Логотип «Такт», имя текущего пользователя с ролью, ссылки: «Проекты», «Пользователи» (только админ), «Выйти».

## 7. Данные

**БД — SQLite, файл `db\task.db`, автосоздание при старте сервера (better-sqlite3, резерв — `node:sqlite`). Без тяжёлых ORM.**

```sql
users (
  id            INTEGER PRIMARY KEY,
  username      TEXT UNIQUE NOT NULL,          -- логин
  display_name  TEXT NOT NULL,                 -- отображаемое имя
  password_hash TEXT NOT NULL,                 -- bcryptjs
  role          TEXT NOT NULL CHECK (role IN ('admin','programmer')),
  is_active     INTEGER NOT NULL DEFAULT 1,
  created_at    TEXT NOT NULL                  -- ISO-8601
)

projects (
  id          INTEGER PRIMARY KEY,
  name        TEXT NOT NULL,
  description TEXT,
  created_by  INTEGER REFERENCES users(id),
  created_at  TEXT NOT NULL
)

tasks (
  id          INTEGER PRIMARY KEY,
  project_id  INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
  title       TEXT NOT NULL,
  description TEXT,
  status      TEXT NOT NULL DEFAULT 'backlog'
              CHECK (status IN ('backlog','in_progress','review','done')),
  priority    TEXT NOT NULL DEFAULT 'medium'
              CHECK (priority IN ('low','medium','high','critical')),
  assignee_id INTEGER REFERENCES users(id),     -- исполнитель
  deadline    TEXT,                             -- дата YYYY-MM-DD
  created_by  INTEGER REFERENCES users(id),
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
)

comments (
  id         INTEGER PRIMARY KEY,
  task_id    INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  author_id  INTEGER NOT NULL REFERENCES users(id),
  text       TEXT NOT NULL,
  created_at TEXT NOT NULL,
  updated_at TEXT
)
```

**Сиды:** указанные в разделе 5 пять аккаунтов + демо-проект «Сайт CakePHP — поддержка» с ~10 задачами (все 4 статуса, все приоритеты, разные исполнители, 3–4 комментария). Идемпотентность: повторный старт сервера не дублирует сид-данные.

**Сессии:** `express-session` (cookie `takt.sid`), secret — из переменной окружения `SESSION_SECRET` с dev-дефолтом; при входе идентификатор пользователя кладётся в `req.session.userId`.

## 9. Требования к адаптивности

- **Desktop (≥1100px):** полноценные 4 колонки канбана рядом; модалка карточки задачи в центре.
- **Tablet (700–1099px):** колонки канбана в горизонтальном скролле (мин. ширина колонки фикс), фильтры сворачиваются.
- **Mobile (<700px):** вход и список проектов одной колонкой; доска — панель-переключатель статуса или горизонтальный скролл со «прилипающим» заголовком колонки; кнопки перемещения статуса достаточно крупные (≥44px).
- Функционал идентичен на всех разрешениях.

## 10. Критерии готовности MVP

- [ ] Запуск одной командой из README на порту 3003; первый запуск не пустой (сиды).
- [ ] Вход/выход; неверный пароль — ошибка; деактивированная учётка не пускает.
- [ ] Ровно 5 демо-аккаунтов могут войти; admin и programmer видят именно свои права.
- [ ] Админ: создать/отредактировать/удалить проект, создать пользователя, деактивировать/активировать, сменить роль/пароль.
- [ ] Любая роль: создать задачу, назначить исполнителя/приоритет/дедлайн, переместить по статусам кнопками, прокомментировать.
- [ ] Фильтры и поиск по доске работают.
- [ ] Презентация приоритета, статуса и исполнителя на карточке читается.
- [ ] Адаптивность на трёх разрешениях проверена глазами.
- [ ] Комментарии: добавлять, редактировать/удалять свои; чужие — только админ.
- [ ] REST API возвращает корректные HTTP-коды и русские сообщения об ошибках; приватные ручки недоступны без сессии; действия программиста не могут менять проекты/пользователей (проверено негативно).

## 11. Вне скоупа

- Установка VCS и интеграция в сайт на CakePHP (нет доступа к сайту, вне рамок урока).
- Самостоятельная регистрация, восстановление пароля через e-mail.
- Вложения файлов к задачам.
- Уведомления (e-mail, пуш, Telegram).
- Drag&drop, тёмная тема, аналитика/бёрндаун, Swagger-документация API.
- Массовое редактирование задач, подзадачи, history/аудит-лог.
- Реальная публикация на Railway / GitHub (выполняет студент по README).
